# KODRO PERFECTION PLAN

Synthesized 2026-07-02 from seven research reports: world-coherence, realism-motion, product-coherence, spec-import, showcase, bugs, engine-fidelity. Research only preceded this document; no code has changed. Every claim below traces to a report; each item cites the originating report and its file:line evidence. Effort scale: S = hours, M = 1 to 2 days, L = 3+ days. Where two reports numbered defects differently (the bugs report and the product-coherence report both use D-numbers), items here carry a unique plan ID and cite the source report explicitly.

---

## 1. Mission statement

Kodro is a proving ground, not a toy. A person who wants to build a real robot, but cannot yet or is skeptical that it will work, imports that robot's actual specifications into Kodro and watches, in a believable world, how the machine they described would actually perform: how fast it really moves, how long its battery really lasts, where it collides, what its sensors can and cannot see, and what it simply cannot do. The product succeeds when a skeptical builder finishes a session with clarity they did not have before, delivered by a fully offline desktop application that feels professional, says exactly what it simulates and what it approximates, and never fakes a number it cannot defend.

## 2. State of the system (honest)

### What is strong

- The quality floor is real and green. 74/74 interpreter QA, 6/6 qa_ui flows, 875 pytest passed with 1 environment skip, and all 36 world x robot combos render and run the starter program to completion with zero JS console errors (bugs report, suite actuals and runtime sweep).
- Motion feel foundations exist and are better than expected: trapezoidal acceleration with mass-derived inertia and momentum carry (app.jsx:813-834, 910), per-robot-type motion personality (Viewport3D.jsx:900-906), weight transfer, banking, suspension and steering dressing (Viewport3D.jsx:1208-1217) (realism-motion).
- The connected loop the product promises does exist in one place: crash, then saved memory reflection, then a diagnostics coach line tying outcome to design (app.jsx:880-905), called the best moment in the product (product-coherence, screen 5).
- Command gating has a single source of truth (window.KodroCommands, RobotLab.jsx:157-210) shared by editor, blocks and AI, with readable refusals (product-coherence).
- City is a strong world: junction, zebra, lit towers, traffic with eased braking, pedestrians with gait animation (world-coherence section 4; Viewport3D.jsx:603-671; agents.jsx:127-188).
- The interpreter is flagship-ready today: def/params/return/recursion, for/while/break/continue, chained comparisons, lists, 10 builtins, dual robot API, verified by a 74-line showcase slice that ran clean through the shipped interpreter with 173 events (showcase, section 5).
- Language-level JS/Python parity is deliberate and good: banker's rounding, int-only range, mirrored clamps (interpreter.js:446-463, 402-409, 761-772) (engine-fidelity).
- Onboarding hero, Robot Lab, and the Help modal are genuinely designed surfaces (product-coherence, journey map screens 1, 6, 16).

### What is weak

- The core loop does not close. The designed robot has no visible identity in the studio (hard-coded OQ-ROVER-04, app.jsx:1653), telemetry shows FRONT LIDAR regardless of build (Telemetry.jsx:91), the Realism dashboard describes the robot's recommended world rather than the world on screen (realism.jsx:34), and the shipped default program scores 0 percent on the product's own Validate button because the goal it grades is never drawn (scenario.jsx:97, 177) (product-coherence D1 to D3).
- Choosing a mission site never rebuilds the 3D scene when the base world is unchanged, because the React key and effect deps use terrain.id, which for a site is the base id (app.jsx:1634, Viewport3D.jsx:1358, terrains.jsx:380-385). Site identity work is invisible until this is fixed (world-coherence BUG-1).
- Of 17 mission sites, only the three indoor bays and the reef read as their names; Fuji has no mountain, Giza no pyramids, Antarctica and Nepal are featureless white voids, Tycho is pixel-identical to base Lunar (world-coherence section 3, screenshots japan.png, egypt.png, antarctica.png, nepal.png, tycho.png).
- Four independent kinematic models simulate the same robot (app.jsx, engine/rover.py, scenario.jsx, selftest.jsx) and they disagree: battery costs differ roughly 11x per metre and 12.5x per degree between JS and Python; a program that visibly crashes can still grade collision-free because register_collision has zero production callers (engine-fidelity, sections 0 and 3).
- The spec import that IS the mission does not exist. The robot spec is a parts-catalogue selection with grams and a unitless speed scalar (RobotLab.jsx:19-45, 103-118); there is nowhere to put wheel radius, torque, battery mAh, or sensor positions (spec-import 1.1; engine-fidelity section 0).
- Two command dialects and two units live side by side (rover.forward(cm) vs move_forward(m)); the AI reviewer's "safe" rewrite silently converts between them, a roughly 20x behaviour change (interpreter.js:41-45, 692, 740; product-coherence D4; bugs D9).
- The app overflows horizontally at 1280x800 and every width from 1100 to about 1355 px; the Settings button sits 56 px offscreen with scrollbars hidden (styles.css:35, 52-57; measured missionbar min-content 1336 px) (bugs D1).
- A REPL error silently swallows the next editor run's completion feedback and lesson grading (replRef leak, app.jsx:1016-1060), proven live via CDP (bugs D2).
- The identity is split: a professional validation studio interleaved with a Key Stage classroom product; emoji are the entire icon system; confetti, achievements and Scratch references sit beside a domain-randomised validator (product-coherence, sections 1 and 4).
- No document model: no project file, no save/open/export, no undo for programmatic editor writes, no run artefact; export APIs in memory.jsx:156-210 are dead code (product-coherence P1, P2, P5).
- Visible realism defects: square particle sprites for bubbles and Mars dust (ambient.jsx:130, 179), a hard-edged grey blob shadow (Viewport3D.jsx:1041-1049), traffic lights that never change (Viewport3D.jsx:650-652), a robot pinned to y=0 floating over displaced terrain (Viewport3D.jsx:254-266 vs 1183), and near-silence after a 0.11 s move blip (sound.js:60) (realism-motion).
- The pymunk physics wrapper is complete but orphaned: never instantiated outside tests (engine/physics.py; engine-fidelity section 0).
- The default first-run program is a 9-line starter; the product's visible ceiling undersells the interpreter (showcase, section 2).

## 4. Sequencing: three milestone cuts

Rationale: fix self-contradiction first (trust), then deliver the mission (spec import plus fidelity plus worlds), then become an application. Each cut is independently shippable and release-taggable; each ends with the full suite matrix green (qa_interpreter, qa_ui, qa_worlds, pytest with -rf).

### Milestone 1: "Coherent" (tag v0.9-coherent)

Everything a skeptical user hits in the first ten minutes stops contradicting itself. Scope: all of P1 (F0 harness first, then F1 to F18), plus the four cheapest realism wins that are visible defects today (R1 round sprites, R2 contact shadows, R3 birds, R4 traffic lights), plus W1 (site atmosphere table, which also fixes BUG-3) and W4/W5 (ambient and agent gating), plus S2/S3 (tab overflow, beep event) as trivial riders.

Why first: the world-coherence report is explicit that nothing site-related matters until F1; the product-coherence report shows the 0 percent Validate and the two-dialect trap are the exact "nothing is connected" moments; the bugs report shows the layout clip hits every common laptop. Ship test: a fresh user at 1280x800 sees no clipped chrome, one dialect, a goal they can see, a Validate verdict about the world on screen, statuses that agree, and no square bubbles.

### Milestone 2: "Proving ground" (tag v1.0-proving-ground)

The mission lands end to end. Scope: P4 SI0 to SI4 (schema, import/export UI, physical mapping, verification report, fidelity badges); P6 E-P2 and E-C4 first, then E-P1, E-A0/A1/A2/A4/A5/A7 (this converts Kodro from animated ledger to first-order predictor and closes the 11x/12.5x battery divergences and the vacuous collision grading); all of P2 (skylines, prop kits, per-site treatments; the Giza pyramids and Fuji cone are the cheapest identity wins); P3 R5 to R9 (ground conformance, sound, water, time of day, car arc turns); P5 S1 plus S6 (Encore ships as the 8th tab with the onboarding CTA replacing the 9-line first impression).

Why second: SI2 and E-A1/A2 are the same hot-path change seen from two reports and must land together behind the presence-of-physical-fields gate, with catalogue mode byte-identical; the verification report (SI3) plus badges (SI4) are the trust story that makes imported numbers defensible. Ship test: import a fixture spec, watch the sim honour its top speed and battery, export a verification report whose measured block agrees with its derived block, in a world that looks like its name.

### Milestone 3: "Professional application" (tag v1.1-studio)

Kodro becomes a document-based pro tool. Scope: P7 A1 to A10 plus A12/A13/A15/A16 (mode split, icons, retheme, copy, themes, merged build, project file, run report, undo, layout persistence, spec-aware grading, arm honesty, validation history, onboarding fold); P5 S4/S5/S7 (Searchlight, Gauntlet, demo hook); P6 E-A3/E-A6 plus Stage C (E-C1, E-C3, E-C5 real-world anchors); P4 SI5/SI6 stretch (URDF subset, pymunk verification lane); P3 R10 plus honourable mentions as capacity allows; P7 A11 (docked panels) last, it is the largest layout change and everything else works without it.

Why third: the document model (A7) and run report (A8) depend on the spec and verification artefacts existing (Milestone 2); the mode split and icon work are high-visibility but zero-dependency and can start any time capacity exists. Ship test: save a project file containing spec, programs, world and history; reopen it cold; run Searchlight to its battery-managed debrief; hand a skeptical builder the run report plus the verification sheet.

## 5. Honest ceilings (what offline/procedural cannot do)

Do not promise past these lines; several are already admitted in docs/known-limitations.md and the SI4 badges exist to say them out loud.

- No downloaded assets, ever. No photoreal textures, no mesh libraries, no GLTF/OBJ loaders (the loaders live in the un-vendored three.js examples tree, docs/known-limitations.md:41-49). World identity comes from primitives, canvas textures and silhouettes; Giza gets pyramid silhouettes, not Giza.
- URDF imports are primitives-only. Any real-world URDF that references mesh files renders as grey placeholder primitives or a named warning (spec-import section 7). Kodro can show a kinematic chain and a reach envelope, not the robot's true collision geometry.
- The visible tick is kinematic, not force-integrated. Even after Stage A, acceleration and braking are first-order closed forms shaping a trapezoid; there is no wheel-level slip physics, no suspension dynamics, no tipping (engine-fidelity sections 1 and 2; body banking is cosmetic per-type constants, Viewport3D.jsx:900-906).
- Worlds are flat planes. Slope capability is a reported number (theta_max) until E-A3 lands, and even then it is procedural slope bands, not real terrain; a slope verdict is a formula, not a driven test (spec-import section 4; engine-fidelity V4).
- No contact dynamics without Stage B. The robot cannot push a crate, glance off a wall, or wedge between obstacles; collisions are stop-and-halt (app.jsx:849-851). Pymunk stays a headless verification lane (SI6) because the pywebview bridge cannot stream 60 Hz and the pure-browser QA harness must keep working (app.py:1024-1033; spec-import section 8).
- The battery model is constant-power. No voltage sag, no thermal derating, no per-motor current transients (SI4 NOT SIMULATED tier). Runtime predictions are honest budgets, not electrochemical simulations.
- Sensors are analytic rays in 2D. Sensor z position is ignored (disclosed); the collision body is a circle, not an oriented box; IMU acceleration content is zero by construction until physics is wired (sensors.py:130-142); camera, GPS, bumper, line and gripper command semantics are not simulated (docs/known-limitations.md:88-112).
- The AI is a local model plus a regex keyword mapper. The onboarding "assistant fits the parts" is keyword mapping (RobotLab.jsx:376-408); Vibe/review quality is bounded by whatever Ollama model is installed locally. No cloud, no accounts, by hard constraint.
- One robot per program. There is no multi-robot addressing in the language (interpreter.js:520, 606); the Swarm button replays one program on several rovers (app.jsx:1493). "Two robots dance together" is out of scope (showcase section 6).
- No trigonometry in user programs until the S8 builtins land; coordinate-computed curves and true bearing math are out of reach today (probe P9), which is why the flagship geometry is turtle-style.
- Fidelity target is first-order agreement, not certification. The acceptance bar is closed-form predictions within about plus or minus 10 percent in E-C1 and landing inside a datasheet's stated range in E-C5. Kodro gives a skeptical builder clarity and honest error bars; it does not replace building the robot.
